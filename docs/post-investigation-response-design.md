# メールアドレス流出調査後の事後対応設計仕様

| 項目 | 内容 |
|---|---|
| 版 | 1.2 |
| 作成日・公式資料確認日 | 2026-10-10 |
| 対象 | 組織が付与した独自ドメインのメールアドレス |
| 対応環境 | Google Workspace、Microsoft 365 |
| 利用者 | セキュリティ担当、メール・ID管理者、端末管理者 |
| 位置づけ | 運用設計案。組織の既存インシデント対応規程を優先する |

流出調査の結果を、認証情報の更新、侵害調査、アカウントの復旧、再発防止へつなげる。メールアドレスの掲載だけで会社のメールシステムが侵害されたとは判断しない。外部サービスの流出と、業務アカウントへの侵害を分けて判定する。

## 1 目的と適用範囲

調査ツールが出力したレポート、利用者からの申告、監視サービスの通知を受け取り、対象アカウントごとに担当者、実施内容、期限、終了条件を決める。

本仕様は人が実施する事後対応を定める。流出データの購入、漏れたパスワードの取得・照合、パスワードを使ったログイン試験、管理操作の自動化は対象外とする。

既存の調査ツール仕様 `SPEC.md` は検出・レポート生成の仕様を管理する。本仕様は、その検出結果を入力とする運用を管理し、調査ツールの振る舞いを変更しない。

## 2 判定の原則

- 流出事件全体にパスワードが含まれていても、対象者の現在の業務パスワードが漏れたとは限らない。
- 流出日、データ公開日、集約リストの作成日、調査による検知日は別々に記録する。
- ハッシュ化されたパスワードも対応判断の対象とする。ハッシュの種類だけを理由に安全と判定しない。
- 古い流出でも、現在のパスワードとの使い回しがあれば対応する。新しい集約リストでも、元の情報は古い場合がある。
- 検出なし、照会失敗、ログが残っていない、確認不可を区別する。確認可能な期間で異常がない場合も、過去を含めた未侵害の証明とはしない。
- インフォスティーラー情報は感染調査の優先度を上げる材料とする。どの端末がいつ感染したか、現在も感染しているかを別途確認する。

## 3 役割と対応目標

| 役割 | 責務 |
|---|---|
| 対応責任者 | 分類、優先順位、停止・復旧判断、終了判定 |
| ID・メール管理者 | ログ保全、アカウント操作、認証・転送・権限の確認 |
| 端末管理者 | EDR調査、端末隔離、修復、利用再開の判断材料の提供 |
| 対象者 | 利用状況と使い回しの申告、本人確認、安全な端末での再登録 |
| 法務・個人情報管理担当 | 実際の侵害や情報持ち出しが判明した場合の通知・報告判断 |

以下は本仕様の運用目標であり、ベンダーの要件ではない。組織の稼働時間と対応体制に合わせて正式な期限を決める。期限内に完了しない場合は責任者に未完了項目を報告する。

| 判定 | 初動の目標 |
|---|---|
| 不正アクセスが進行中または強く疑われる | 検知直後に封じ込めを開始 |
| 業務認証情報への影響、感染情報あり | 当日中に本人確認と管理ログ・端末の確認を開始 |
| アドレス・プロフィールだけの流出 | 3営業日以内に確認を開始 |
| 照会失敗・情報不足 | 当日中に担当者と再確認期限を設定 |

管理者、経理、役員、共有メール、回復用アカウントは同じ判定でも優先する。

## 4 調査結果の受付と名寄せ

1. 調査実行日時、利用プロバイダ、対象範囲、照会失敗・スキップを記録する。
2. 対象アドレスを社員台帳・ID台帳に照合する。主アドレス、エイリアス、旧アドレス、共有アドレスを同じアカウントに紐づける。
3. 現役、退職、停止済み、存在しないアドレスを区別する。過去に別人へ割り当てられたアドレスは、流出当時の利用者を確認する。
4. 対象者に、流出元サービスの利用、流出後の変更、業務アカウントとの同一・類似パスワード利用を確認する。パスワードそのものは提出させない。
5. 外部SSO、オンプレミスAD、別のIdPが認証元の場合は、その管理者を対応に加える。

退職者のアカウントが有効なら停止とセッション失効を優先する。停止済みの場合も、転送、委任、外部SaaSの残存アクセスを確認する。

## 5 対応区分

| 区分 | 判定条件 | 必須対応 |
|---|---|---|
| R1 侵害疑い・確認済み | 本人に説明できない成功ログイン、不正送信、未知の転送・OAuth同意・認証方法など | 一時停止、セッション失効、証拠保全、侵害範囲調査 |
| R2 認証情報への影響 | 業務パスワードの使い回しあり、またはパスワードを含む流出で変更・重複を確認できない | 影響する業務・外部サービスのパスワード変更、セッション失効、MFA確認 |
| R3 外部サービスの認証情報のみ | 会社とは別のパスワードと確認でき、業務侵害の兆候なし | 外部サービスの更新確認、業務ログ・設定確認、注意喚起 |
| R4 アドレス・プロフィールのみ | パスワードを含まない流出で、業務侵害の兆候なし | 業務ログ・設定確認、MFA確認、注意喚起 |
| R5 情報不足 | 未照会・照会失敗、情報種別不明など | 再照会、追加確認、責任者による暫定判定 |

感染情報がある対象は、R1の兆候がなくても当日中に端末調査する。感染・トークン窃取が疑われればR1へ移す。海外IPだけでR1とせず、本人、VPN、端末、アプリ、操作履歴を照合する。

調査ツールの `critical/high/medium/low/none/unknown` は確認順序の入力であり、R1〜R5を自動決定しない。`critical` は感染情報の調査、`high/medium` は使い回しと変更時期の確認、`low` はアドレス流出の確認を優先する。`partial/unknown` は未確認範囲を残す。日付不明を安全の根拠にしない。

## 6 共通の証拠保全

保存対象は認証・監査ログ、設定の変更前の状態、不審メールのヘッダーとメッセージID、アプリIDと権限、端末検知、実施操作の日時・実施者とする。

時刻のタイムゾーン、検索条件、取得元、対象期間を必ず記録する。元のエクスポートは変更せず保管し、分析用コピーを作る。必要に応じてSHA-256と取得者を記録する。停止・リセット・削除の前後を区別する。

進行中の攻撃では、保全完了を待って封じ込めを遅らせない。停止と保全を並行し、順序と時刻を記録する。アカウントやメールボックスの削除を封じ込め手段にしない。

実際の証拠、氏名、アドレス、端末・IP情報、APIキー、復旧コードはGitHubに格納しない。組織が承認したアクセス制限付き保管先で、閲覧者、保持期限、削除責任者を決める。

## 7 Google Workspaceの対応

### 7.1 ログと設定の確認

管理画面は [Google Admin](https://admin.google.com/) を利用する。

「レポート → 監査と調査」でユーザーと期間を指定する。直近30日を初期範囲とし、不審な時刻が分かれば前後へ広げる。30日は運用上の目安であり、保持期間を保証するものではない。

| 確認先 | 確認項目 |
|---|---|
| ユーザーログイベント | ログイン、認証設定変更、セッション警告。日時、IP、本人の利用状況を照合 |
| OAuthログイベント | 新規認可、不審なアプリ、要求・付与された権限 |
| Driveログイベント | 大量ダウンロード、外部共有、共有権限変更 |
| 管理者ログイベント | 管理権限、Gmailルーティング、セキュリティ設定の変更 |
| メールログ検索 | 不審な送信、送信先、配送状況 |

旧画面ではログイン・ユーザーアカウントのログが分かれている場合がある。Driveでは主アドレスを検索する。メールログ検索の配送結果だけで、メール閲覧や持ち出しの有無を判定しない。[G1][G2][G3]

「ディレクトリ → ユーザー → 対象ユーザー → セキュリティ」で、取得可能な認証情報、アプリパスワード、認可済みアクセスを確認する。利用者と認証方法・回復先を照合する。

Gmail設定は本人立ち会い、または承認されたGmail APIによる取得で確認する。管理者が全ユーザーの全設定を管理画面だけで閲覧できるとは想定しない。API用のドメイン全体の委任は、必要性・権限・期間を確認してから設定する。

| Gmail設定 | 確認項目 |
|---|---|
| メール転送とPOP/IMAP | 外部転送先、不審なアクセス設定 |
| フィルタとブロック中のアドレス | 転送、削除、既読化、受信トレイをスキップするルール |
| アカウント | 委任先、送信元設定 |

組織のGmailルーティング設定も、管理者が侵害された場合は確認する。[G3]

### 7.2 封じ込めと認証情報の更新

R1では以下を実施する。R2では停止の要否を責任者が判断し、影響する認証情報の変更とセッション失効を実施する。

1. 「ディレクトリ → ユーザー → 対象ユーザー」でユーザーを一時停止する。
2. ログと設定を保全する。
3. パスワードをリセットする。外部IdPを使う場合は認証元でも更新する。
4. 対象ユーザーの「セキュリティ → ログインCookie」でリセットする。
5. 認可済みアクセスから不審なアプリのアクセスを取り消す。パスワード変更で全OAuthアクセスが消えるとは考えない。
6. 不審な認証方法、回復先、転送、フィルタ、委任を除去する。認証方法の再登録は別経路で本人確認してから行う。
7. 端末感染の有無を確認する。疑わしい端末では再ログイン・新しいパスワードの入力を行わない。

パスワード変更とログインCookieリセットを組み合わせる。Googleの案内では、パスワードリセット時にアプリパスワードは失効するが、既に端末に同期されたデータは回収されない。[G4]

組織で不審なOAuthアプリを制限する場合は、「セキュリティ → アクセスとデータ管理 → APIの制御 → アプリのアクセス制御」を使う。アプリID、権限、適用範囲、正規利用への影響を記録する。[G5]

## 8 Microsoft 365の対応

### 8.1 ログと設定の確認

管理画面は [Microsoft Entra](https://entra.microsoft.com/)、[Exchange](https://admin.exchange.microsoft.com/)、[Microsoft Purview](https://purview.microsoft.com/) を利用する。

| 確認先 | 確認項目 |
|---|---|
| Entraの対象ユーザーのサインインログ | 対話型・非対話型の両方。IP、端末、アプリ、リソース、認証結果、条件付きアクセス |
| Entra監査ログ | 認証方法追加、回復情報・パスワード変更、アプリ同意、権限変更 |
| 対象ユーザーの認証方法 | 未知のAuthenticator、電話番号、パスキー等 |
| Exchangeのメールボックス | 外部転送、委任権限、受信トレイルール |
| Purviewの監査 | 利用可能なメール・SharePoint・OneDrive操作、外部共有・ダウンロード |
| Exchangeのメッセージ追跡 | 不審な送信、送信先、配送状況 |

既存トークンの利用を調べるため、非対話型のログも対象にする。「MFA成功」だけでは本人の操作と断定しない。本人の利用、端末、アプリ、実際の操作を照合する。[M1][M2]

Exchange Online PowerShellへ必要な権限で接続した後、次の読み取りコマンドで転送と非表示ルールを確認する。アドレスは調査対象に置き換える。

```powershell
Get-Mailbox -Identity user@example.com |
  Format-List ForwardingAddress,ForwardingSmtpAddress,DeliverToMailboxAndForward

Get-InboxRule -Mailbox user@example.com -IncludeHidden |
  Format-List Name,Enabled,RedirectTo,ForwardTo,ForwardAsAttachmentTo,DeleteMessage,Identity
```

削除は結果を保全して正規設定か確認してから行う。メールボックスの代理アクセス、Send As、Send on Behalfの委任も確認する。[M3]

### 8.2 封じ込めと認証情報の更新

R1では以下を実施する。R2では停止の要否を責任者が判断し、影響する認証情報の変更とセッション失効を実施する。

1. Entraの「ユーザー → すべてのユーザー → 対象ユーザー」でアカウント状態を編集し、アカウントを無効化する。
2. 対象ユーザーの「概要」で **Revoke sessions** を実行する。
3. ログと設定を保全する。
4. パスワードをリセットする。オンプレミスAD・外部IdPが認証元の場合は認証元でも対応する。
5. 不審な認証方法を除去し、必要に応じて本人確認後にMFAを再登録する。
6. 不審なOAuth同意・アクセス権を取り消し、転送、受信ルール、委任を除去する。
7. 端末感染と、外部SaaSの残存アクセスを確認する。

「MFAセッションの取り消し」を通常のセッション取り消しの代用にしない。セッション失効の反映はアプリとトークンによって異なる。Entraが外部アプリ独自のセッションを直接取り消せない場合は、そのアプリでも失効・利用停止を行う。停止後のアクセスを監視し、操作直後の完全遮断を前提にしない。[M4]

## 9 侵害範囲の確定と追加対応

R1では最初の不審操作から封じ込め後までの時系列を作り、次を調べる。

- メールの不正送信、転送先への配送、閲覧・取得について確認可能な証拠。
- Drive・SharePoint・OneDriveのアクセス、外部共有、ダウンロード。
- 他の社員、管理者、共有メール、外部SaaSへの波及。
- 振込先変更、請求書差し替え、パスワード再設定メールの悪用。
- 感染端末で利用した認証情報やセッションへの影響。

他アカウントや端末への波及が見つかれば別の対象として登録する。不正な振込依頼などがあれば、経理・責任者へ即時に連絡し、既知の電話番号など別経路で取引を確認する。

個人情報・顧客情報の持ち出し、不正送信などが確認または疑われる場合は、法務・個人情報管理担当が法令、契約、社内規程に照らして通知・報告の要否と期限を判断する。本仕様だけで対外報告の必要性を決定しない。

## 10 復旧と終了条件

R1の利用再開には、責任者が次の条件を確認する。

- 証拠を保全し、不審な設定とアクセス権を除去した。
- 本人を別経路で確認し、安全な端末から専用のパスワード・MFAを設定した。
- 感染が疑われた端末は隔離・調査し、修復または再構築後の安全を確認した。
- アクセス再開の対象、未解決事項、監視担当者を記録した。

再開後、正常ログイン・メール送受信を確認する。運用目安として翌営業日と1週間後に、ログイン、転送、認証方法、OAuth権限を再確認する。再発時は再度封じ込める。

| 区分 | 終了条件 |
|---|---|
| R1 | 侵害範囲・不明範囲を記録、必要な封じ込め・修復・通知判断を完了、再確認で再発なし |
| R2 | 影響する認証情報の変更・セッション失効・MFA確認、ログと設定の確認を完了 |
| R3 | 流出元の更新状況、業務との重複なし、ログ・設定・注意喚起を記録 |
| R4 | ログ・設定・MFA確認と注意喚起を記録 |
| R5 | 追加確認で再分類、または残る不確実性と監視・再確認計画を責任者が受け入れた |

終了時の結論は「侵害確認」「侵害疑い・確定不能」「確認範囲では兆候なし」を使い分ける。ログが取得できなかった項目は「確認不可」とする。

## 11 再発防止

1. 業務アカウントのMFAを必須化し、管理者にはフィッシング耐性のあるパスキー・セキュリティキーを優先する。
2. 会社が承認したパスワード管理ツールで、サービスごとに異なるパスワードを管理する。
3. 管理者アカウントを通常業務から分け、回復・緊急アクセスの手段を点検する。
4. 外部転送、OAuthアプリ同意、レガシー認証の利用を棚卸しし、必要なものに制限する。
5. 不審ログイン、認証方法変更、外部転送などの通知を、利用可能な機能で設定する。
6. ログ保持・取得手順と退職者のアクセス停止を定期点検する。

SPF・DKIM・DMARCは送信ドメインのなりすまし対策として別途点検するが、認証情報の流出や正規アカウントの侵害対応を代替しない。流出だけを理由にドメインを変更しない。アドレス変更が必要な場合は、業務影響と旧アドレスの転送・回復用途を確認する。

## 12 記録様式

実案件はこの項目を社内チケットへコピーし、アクセス制限付きの証拠保管先と紐づける。

| 項目 | 記録内容 |
|---|---|
| 案件ID・担当 | 社内管理番号、責任者、実施者 |
| 対象 | 主アドレス、エイリアス、在籍状態、権限、メール基盤、認証元 |
| 検知情報 | 検知日時、プロバイダ、流出元、流出日・公開日、データ種別、照会範囲 |
| 本人確認 | 確認方法、使い回しの有無、変更状況。秘密情報は記録しない |
| 判定 | R1〜R5、根拠、未確認項目、期限 |
| 証拠 | 保存先、取得条件、期間、タイムゾーン、取得者、取得日時 |
| 実施操作 | 停止、リセット、失効、権限・設定解除の対象、実施者、日時、結果 |
| 影響 | メール・ファイル・金銭・他アカウントへの影響、確認不可の範囲 |
| 復旧 | 本人確認、端末確認、MFA設定、責任者の判断、再開日時 |
| 終了 | 翌営業日・1週間後の再確認、通知判断、結論、残存リスク、保管期限 |

## 13 利用者への連絡文面

### 13.1 パスワード変更の依頼

回答を求めるだけではリスクは減らないため、まず変更を指示し、変更の完了と会社アカウントでの使い回しの有無を報告させる。調査ツールのレポート（SPEC §10.5.3）には、アドレスごとに「本人が行うこと」の表（対象サービスごとの変更と完了の条件）が出る。この文面にその表を添えて渡し、すべての行が完了するまで追う。

> 外部サービスの流出情報に、会社のメールアドレスが含まれていました。社内チケットに記載したサービスのパスワードを、直ちに変更してください。同じ、または似たパスワードを会社のアカウントやほかのサービスで使っている場合は、それらもすべて直ちに変更してください。多要素認証を使えるサービスでは、有効にしてください。変更が終わったら、セキュリティ窓口に「変更した」ことと、「会社のアカウントで同じ・似たパスワードを使っていたか」を知らせてください。パスワード・認証コードは送らないでください。

パスワードを含まない流出（R4 相当）では、変更の依頼ではなく、レポートの「本人が行うこと」（なりすましメールへの備え）を指示する。感染情報がある対象には、端末調査が終わるまでその端末で新しい認証情報を入力しないよう伝える（13.2 と同じ趣旨）。

### 13.2 一時停止の連絡

> 不審なアクセスを調査するため、対象アカウントを一時停止しました。復旧作業はセキュリティ担当が別経路で本人確認したうえで案内します。調査対象の端末では、新しい認証情報を入力せず、担当者の指示に従ってください。

乗っ取りが疑われるメールだけを連絡経路にしない。社内の既知の電話番号や対面などを利用する。

## 14 運用開始前の確認と受入基準

| ID | 確認内容 |
|---|---|
| A1 | GWS・Microsoft 365それぞれで停止、失効、ログ取得に必要な役割と代替担当者が決まっている |
| A2 | 契約で利用できるログ・保持期間・API・監査機能と、取得不可の項目を記録している |
| A3 | テストアカウントで停止、リセット、セッション失効、MFA再登録、復旧を確認している |
| A4 | テスト用の転送・フィルタ・OAuth権限を記録し、正規設定と区別して解除できる |
| A5 | 外部SSO・外部SaaSの停止・失効手順と窓口が決まっている |
| A6 | R1〜R5の模擬案件で担当・期限・終了条件を決定できる |
| A7 | 実案件の情報を公開リポジトリへ格納しない保管手順がある |

本番への制御変更は、小規模な対象で業務影響と回復方法を確認してから展開する。仕様の更新時は、画面の変更、ベンダーの仕様、社内規程への影響を確認する。
